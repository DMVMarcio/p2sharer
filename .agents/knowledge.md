# Workspace Technical Knowledge Base: P2Sharer

## 1. Project Overview & Architecture
P2Sharer is a serverless, peer-to-peer screen and application audio sharing desktop application built on Tauri v2. It provides high-performance desktop/window streaming with hardware acceleration, native Windows WASAPI loopback audio capture with process-level filtering, and a resilient decentralized WebRTC mesh network with zero central media servers.

- **Ecosystem & Stack**:
  - **Host Framework**: Tauri v2 (`@tauri-apps/api: ^2`, `@tauri-apps/cli: ^2`, `tauri-plugin-opener: ^2`)
  - **Backend**: Rust 2021 edition (`src-tauri/`), Windows Win32 / Core Audio APIs (`windows: 0.58`), `xcap: 0.9.8`, `tokio: 1`, `tokio-tungstenite: 0.24`, `rayon: 1.10`, `sysinfo: 0.32`, `image: 0.25`
  - **Frontend**: React 18, TypeScript 5.6, Vite 6 (`src/`), Web Audio API, Lucide icons (`lucide: ^1.31.0`, `lucide-react`), Pako compression (`pako: ^3.0.1`)
  - **Networking & P2P**: Trystero (`@trystero-p2p/mqtt`, `@trystero-p2p/nostr`, `@trystero-p2p/torrent`, `trystero: ^0.25.3`), WebRTC mesh with multi-transport signaling failover
- **Primary Design Pattern**:
  - Event-driven, decoupled modular architecture.
  - Rust side: Asynchronous Tokio runtime, event-driven audio loopback, thread-safe broadcast channels for video streaming.
  - Frontend side: React 18 component tree (`components/`), specialized custom hooks (`hooks/`), central reactive state store (`core/state_store.ts` with `useStore`), and service coordinator (`services/room_service.ts`).
- **Core Entrypoints**:
  - Frontend: `src/main.tsx`, `src/App.tsx`
  - Backend Rust: `src-tauri/src/main.rs`, `src-tauri/src/lib.rs`
  - Shell / UI: `index.html`, `src/style.css`

- `[UI]` **Canonical Reuse**: Search `src/ui/` and `src/style.css` before authoring new elements. Never create ad-hoc inline styles or unmodular UI components. Maintain dark/light theme tokens and accent colors.
- `[Video]` **Hardware Acceleration**: Preserve WebView2 GPU acceleration flags in `src-tauri/src/lib.rs` and SDP codec priority (H.264/AV1/VP9/VP8) in `MediaCoordinator`.
- `[Video]` **Windows Graphics Capture (WGC) & Zero-Copy 60 FPS Pipeline**: Screen and window sharing uses the native Windows Graphics Capture API via `windows-capture` to capture Direct3D11 frames directly from the DWM compositor in <0.5ms with hardware cursor compositing and borderless capture. To prevent WebRTC starvation when the screen is static or running 24-30 FPS content, a zero-drift 60 FPS heartbeat pacer thread with `MultimediaTimerGuard` continuously emits cached frames or 1-byte ticks with a ~22.5ms dynamic threshold (`target_interval_us + slack`), sustaining a solid 60.0 FPS clock. Resizing uses SIMD `fast_image_resize` with `FilterType::Bilinear` convolution for ultra-fast SIMD downsampling (<0.8ms vs 15ms Catmull-Rom), preventing gaming CPU bottlenecks. The software arrival gate permits frame intervals up to 2x target FPS (`1_000_000_000 / (fps * 2)`), ensuring natural DWM VSync +/- 1.5ms jitter never triggers false-positive frame drops. JPEG encoding uses SIMD 4:2:0 chroma sampling at quality 80 (`SamplingFactor::R_4_2_0`), producing compact ~45KB payloads that decode in <2ms via `createImageBitmap(blob, { premultiplyAlpha: 'none', colorSpaceConversion: 'none', resizeQuality: 'pixelated' })` without CPU decode queue backpressure. WebRTC video tracks strictly enforce `contentHint = 'motion'` and `degradationPreference = 'maintain-framerate'` to prohibit Chromium from engaging screenshare 25 FPS throttling. WebCodecs `MediaStreamTrackGenerator` and `VideoFrame` feed frames directly into WebRTC transceivers, with WebView2 flags enabling hardware video/MJPEG decoding and disabling background timer throttling (`--disable-background-timer-throttling --disable-renderer-backgrounding --disable-backgrounding-occluded-windows`). Fallback canvases are attached to the DOM to prevent Chromium power-saving frame rate throttles. All transmission is in-app without Chromium browser dialogs or technical jargon ("GPU Direta").
- `[Video]` **Zero-Overhead Transmission & Mirror Loop Prevention**: To keep CPU usage under 2-3% during 1080p 60fps transmissions, the native Rust capture pacer loop de-conflicts with WGC by checking `pacer_wgc_last_sent_us`. When WGC is actively delivering frames at 60 FPS (e.g. during gaming), the pacer detects active motion (< 22.5ms threshold) and stays dormant, preventing 120 FPS frame bursts and WebRTC queue congestion. During static screen or low-fps video periods, it emits 1-byte heartbeat ticks (`Message::Binary(vec![0])`) at 60 FPS, sending a full keyframe once per second (~60 ticks). The frontend `NativeVideoBridge` intercepts 1-byte ticks and bypasses `Blob` allocation and `createImageBitmap` CPU decoding, reusing the GPU-cached `ImageBitmap` to construct `new VideoFrame(this.latestBitmap)` with strictly monotonic microsecond timestamps. Crucially, incoming dummy ticks never overwrite real JPEG frames awaiting decode in `pendingBuffer`. Furthermore, `VideoCard.tsx` renders a lightweight transmission card (`.local-broadcaster-placeholder`) for the local broadcaster instead of mounting an unthrottled local `<video>` mirror element. This eliminates the recursive hall-of-mirrors feedback loop where the local video playback constantly invalidated screen pixels, triggered false WGC motion capture, and pegged WebView2 CPU at ~23%. Users can toggle live preview on demand with "Ver Prévia" / "Ocultar Prévia". In `style.css`, `.local-broadcaster-radar-pulse` uses GPU-composited `transform` and `opacity` animations instead of continuous `box-shadow` repaints to ensure zero CPU compositor overhead.
- `[Video]` **Windows Graphics Capture (WGC) DirectFlip & Fullscreen 3D Gaming**: DirectX 11/12 and Vulkan games running in exclusive fullscreen or borderless window engage DirectFlip / Independent Flip (MPO scanout bypass), bypassing DWM desktop composition. Setting `MinimumUpdateIntervalSettings::Custom(...)` calls WinRT `SetMinUpdateInterval`, which relies on DWM compositor ticks. Under DirectFlip, DWM composition is dormant, causing frame arrival callbacks to stall or drop to ~0-1 FPS. Always use `MinimumUpdateIntervalSettings::Default` on WGC capture sessions; software rate-limiting (`min_frame_interval = 1s / (fps * 2)`) inside `on_frame_arrived` handles framerate capping without DWM dependencies. In `NativeWgcHandler::on_frame_arrived`, transient DXGI errors during surface lock or swapchain recreation are caught gracefully (`match frame.buffer()`) without returning `Err`, preventing `windows-capture` from aborting the capture loop via `PostThreadMessageW(WM_QUIT)`. To prevent Windows Game Mode from throttling background capture threads, process priority is elevated to `HIGH_PRIORITY_CLASS` during active capture and restored to `NORMAL_PRIORITY_CLASS` on teardown.
- `[Video]` **WebRTC Degradation Preference & Screen Resolution Preservation**: In WebRTC, setting `degradationPreference = 'maintain-framerate'` instructs Chromium's `VideoStreamEncoder` / `QualityScaler` to aggressively downscale resolution (1080p -> 720p -> 540p -> 360p -> 270p -> 180p) whenever transient packet delay or bandwidth estimation (BWE) fluctuates. For screen, window, and game streaming, `degradationPreference` MUST be explicitly set to `'maintain-resolution'` on `RTCRtpSendParameters`, with `scaleResolutionDownBy = 1.0` across all encodings. Concurrently, `contentHint = 'motion'` on the video track prevents Chromium from throttling framerate to 25 FPS, allowing a 60 FPS clock. If network congestion occurs, WebRTC adapts by dropping framerate slightly rather than degrading visual clarity or blurring text.
- `[Audio]` **Process Isolation & Sync**: Keep WASAPI loopback event-driven (<20us latency). Ensure ITU-R BS.775 downmixing and fractional 48kHz resampling phase continuity across streaming chunks.
- `[Audio]` **Windows WASAPI Process Loopback & Resilience**: `VAD\Process_Loopback` requires `AUDCLNT_STREAMFLAGS_LOOPBACK` on `IAudioClient::Initialize` (omitting it yields `0x88890021` / `AUDCLNT_E_INVALID_STREAM_FLAG` and total silence). Always fallback to master audio (`get_default_render_audio_client()`) if process loopback activation fails. Process lists in `process_manager.rs` deduplicate instances by executable name while tracking active window titles. Both "exclude" and "include" modes support multi-selection via standard checkboxes. Because Windows `AUDIOCLIENT_PROCESS_LOOPBACK_PARAMS` natively accepts only a single `TargetProcessId`, multi-process exclusion cannot be executed via a single loopback client. When 2 or more processes are excluded, P2Sharer executes dynamic session inversion: it queries active audio sessions via `IAudioSessionEnumerator` on `IAudioSessionManager2`, isolates all non-excluded processes using `PROCESS_LOOPBACK_MODE_INCLUDE_PROCESS_TREE`, mixes their stereo streams with `WaitForMultipleObjects`, and runs a 500ms periodic heartbeat to dynamically attach newly launched sessions and purge dead processes. When exactly 1 process is excluded, it uses native kernel exclude loopback; when 0 are excluded, it captures master loopback. Audio modal UI must remain sober, native-feeling, and free of AI-slop (segmented tab controls, clean search, subtle badges, no glowing neon box-shadows or verbose paragraphs).
- `[P2P]` **Ghost Peer Mitigation & WebRTC Connection-Guarded Pruning**: Enforce strict direct WebRTC verification; quarantine BitTorrent PEX gossip rumors while actively bridging indirect peers via in-mesh data channels to form resilient full-mesh topologies. Heartbeat pruning defaults to 25s timeout and must ALWAYS inspect `RTCPeerConnection.connectionState` before pruning. If the WebRTC peer connection is `connected`, the peer is physically alive (data channel heartbeats may merely be delayed by video congestion), so `touchPeer` refreshes the slot instead of dropping the peer.
- `[P2P]` **Default OpenRelay Fallback TURN for Symmetric NAT / CGNAT Traversal**: In consumer broadband/mobile environments where both peers are behind Symmetric NAT (or CGNAT), STUN-only reflexive UDP hole-punching inherently fails. Due to Chromium's 45s ICE timeout and Trystero's 180s offer lease TTL, discovery can stall for 3 to 4 minutes without relay candidates. `DEFAULT_FALLBACK_TURN_SERVERS` provides resilient OpenRelay endpoints on ports 80, 443, and TLS 443 over TCP. `buildIceServers` automatically attaches fallback TURN relays when no custom TURN is configured in settings, enabling sub-second WebRTC connection establishment.
- `[P2P]` **Instant PEX Gossip Visibility & Connecting State**: In 3+ participant rooms where peer A connects to B and peer B connects to C, B gossips C's existence to A via PEX. To avoid ghost/invisible peer bugs where C is absent from the UI during WebRTC negotiation, `peer_tracker.ts` exposes `getAllRoomPeers()`, rendering active rumors as `connectionState: 'connecting'` and verified peers as `connectionState: 'connected'`. `GroupRoomManager` immediately dispatches `notifyPeersUpdate()` upon receiving PEX rumors.
- `[P2P]` **Primary Transport Reset on Room Join & Drift Prevention**: In `SignalingManager`, `joinRoom` and `leaveRoom` must deterministically reset `activeTransport = 'mqtt'`, `consecutiveStalls = 0`, and `isFailingOver = false`. This guarantees that if transport failover ever triggered during a previous session or network blip, the application never remains trapped in an alternate signaling realm (Nostr or Torrent) where other peers in the room (who are on MQTT) are invisible, eliminating the bug where users were forced to restart the desktop app repeatedly to connect.
- `[P2P]` **Proactive Rendezvous and Passive Joiners**: Trystero discovers peers on SHA-1 room and peer MQTT topics. Active creators dispatch rapid presence beacons at 100ms, 400ms, 1000ms, and 2200ms and continue while alone. Joiners are passive until an existing active peer is found; they must not issue manual broker beacons before that first direct handshake. Once connected, targeted reannouncements and PEX help close missing mesh edges.
- `[P2P]` **MQTT Health Must Use Real Trystero Sockets**: `signalingManager.getRelaySockets('mqtt')` reports the Trystero relay sockets only. The existence of `activeRoom` or a separately connected MQTT probe never proves that Trystero has subscribed successfully. The watchdog allows the 4-second startup grace period and the required two 1.5-second stalls before failover.
- `[P2P]` **Room Lifecycle Async Guard**: `RoomService.joinRoom` must always asynchronously `await` previous `roomManager.leave()` before constructing a new room. `SignalingManager.leaveRoom(targetRoom?)` verifies room instance identity to ensure stale async leaves from earlier sessions never destroy a freshly initialized room's active signaling session.
- `[P2P]` **Real MQTT Probe Keep-Alives**: Public MQTT brokers terminate raw WebSockets after 5s if no MQTT `CONNECT` packet is received. Signaling probes must maintain genuine `mqtt.connect` clients with active keep-alive pings (`PINGREQ`/`PINGRESP`) to prevent false-positive relay drops and premature watchdog failover.
- `[P2P]` **In-Mesh Broker Re-Announcement**: Trystero `makeAction` channels operate strictly over existing WebRTC data channels, not signaling brokers. When indirect peers are gossiped via PEX or signaled via `mesh_hello`/`mesh_ack`, peers must call `signalingManager.reannounce(topic, targetPeerId)` to publish directly to Trystero's computed SHA-1 MQTT topics (`Trystero@appId@topic` and `...topic@targetPeerId`), prompting Trystero to immediately generate and exchange WebRTC SDP offers between the indirect pair.
- `[P2P]` **Room Roles and Signaling Synchronization**: The creator uses an active Trystero room and advertises it; joiners use `config.passive` and listen until an active room announcement arrives. Manual MQTT reannouncements are allowed for the creator or a joiner with a verified direct peer. Keep the 4-second startup grace and two 1.5-second stalls. Automatic transport failover is deferred while any direct WebRTC peer is active, preserving the live mesh and avoiding signaling splits.
- `[P2P]` **Transport Replacement Isolation**: Before replacing a Trystero room, retire direct peer edges because the old room's channels are closing. Every room lifecycle listener and action handler checks its bound room instance so late callbacks cannot alter the new room. `RoomService` serializes join and leave transitions and ignores callbacks from obsolete managers.
- `[P2P]` **Idempotent Watch Actions**: Stream watching actions (`watchStream`, `stopWatchingStream`, `watch_status`) must be strictly idempotent to prevent audio chirping loops (`playWatchStreamStart`) and redundant signaling bursts.
- `[UI]` **React HUD Exclusivity**: All stream card overlays, stats HUDs (FPS, resolution, bitrate, ping), and tooltips must be rendered declaratively within React components (e.g. `VideoCard.tsx`). Legacy controllers like `HudController` must never query or mutate `.stream-card` DOM elements directly.
- `[UI]` **PiP Signaling Transport**: A PiP session must use exactly one signaling transport at a time. In Tauri, use native events; in browser-only mode, use `BroadcastChannel`. Broadcasting every offer, answer, and ICE candidate through both transports delivers duplicate messages and can race WebRTC negotiation. Serialize offer creation and defer a stream-change offer until the peer connection returns to `stable`.
- `[UI]` **PiP React Lifecycle**: PiP window cleanup must not emit `pip-close` from a React effect cleanup. React Strict Mode deliberately runs an effect cleanup during its development probe; emitting a close signal there destroys the main-window WebRTC sender before the PiP receiver can render its track. Send that signal only from the real `beforeunload` event or the explicit close action.
- `[UI]` **PiP Stream Request Readiness**: In a PiP effect, wait for the asynchronous Tauri event listener to register before scheduling the first `pip-ready` request. Schedule it through a cancelable timeout so Strict Mode's probe effect is disposed before it can create a stale offer. Clear the timeout and retries in cleanup.
- `[UI]` **Shared Stream Statistics HUD**: `StreamStatsOverlay` is the single source for the stream-card and PiP metrics HUD. Pass transport, bitrate, ping, and watcher data into it instead of recreating badges, so their styles and tooltips remain identical.
- `[UI]` **Stream Zoom & Precision Slider**: Stream viewer cards support focal-point wheel/pinch zoom (1.0x to 5.0x) with hardware-accelerated `translate3d` and GPU scaling. Mouse dragging pans the zoomed stream with boundary clamping. When zoom exceeds 1.0x, a precision control bar (`ZoomControlBar.tsx`) appears in the bottom-right corner with range slider, step buttons, percentage readout, and quick reset. Double-clicking on the zoomed video resets zoom to 1.0x.

The main spotlight stage retains full badges and labels. Global stream filters (`all`, `streaming`, `watching`) can be toggled via header pills with real-time participant counts positioned on the left side of `StreamHeaderBar`.

- `[Video]` **Native Windows Screen Capture (WGC) & Stream Performance**: Windows Graphics Capture (WGC) and xcap frame encoding in `src-tauri/src/screen_sources.rs` configure `jpeg_encoder` with `SamplingFactor::R_4_2_0` and quality 90-92 (clamped 60 to 95). SIMD 4:2:0 chroma sampling slashes CPU encoding times down to 2-3ms (compared to 12-15ms under 4:4:4) and decoder `createImageBitmap` latency down to <1.5ms, guaranteeing rock-solid 60 FPS delivery within the 16.6ms frame budget. Visual sharpness and text clarity are preserved through the forced 8–25 Mbps WebRTC SDP bitrate floor/ceiling (`b=AS:25000`, `b=TIAS:25000000`, `x-google-min-bitrate=8000`) and `contentHint = 'detail'`, completely avoiding rate controller downsampling. The heartbeat pacer thread enforces a 66ms static threshold (`target_interval_us * 4`), staying dormant during active mouse and screen movements so it never injects stale frames or causes cursor judder/teleportation. Receiver jitter buffers are tuned to 20ms (`playoutDelayHint = 0.02`, `jitterBufferTarget = 20`) to eliminate frame dropping from network/OS scheduling jitter.
- `[UI]` **Layout Mode Exclusivity & Single-Instance Video Pipelines**: In `RoomVideoContainer.tsx`, stream cards are conditionally instantiated only for the active layout mode (`layoutMode === 'grid'` vs `layoutMode === 'spotlight'`). Additionally, `GroupRoomManager.getPeerStats` caches WebRTC stats with an 800ms TTL and guards against sampling deltas <500ms, while `VideoCard.tsx` permanently renders the remote bitrate badge (never returning `null`) with a 600ms initial fast timer, preventing HUD bitrate badge flickering.

- `[Performance]` **Idle & In-Room CPU Conservation**:
  - **Frontend Logger Singleton**: `initFrontendLogger` must be protected by a singleton guard (`isLoggerInitialized`) to prevent recursive `console.log` wrapping on React re-renders. Only significant lifecycle events (`[P2P] Joining`, `[P2P] Direct WebRTC peer`, `[P2P] Peer left`), warnings, errors, and unhandled rejections should be forwarded over Tauri IPC.
  - **Disk Write Buffering**: Tauri logger must not execute synchronous `file.flush()` (Windows `FlushFileBuffers`) on individual log writes; OS write caching is used, flushing only before opening logs.
  - **WebRTC Stream Recovery Validation**: Never compare receiver `MediaStream.id` to broadcaster `stream.id` across WebRTC (the browser generates a random local MediaStream UUID for incoming tracks). Track the broadcaster's advertised `streamId` explicitly in `lastBroadcasterStreamIds`, and enforce an 8-second debounce (`lastStreamRecoveryRequests`) before dispatching `stream_req`.
  - **PEX Mesh Rumor Bridging & Intermediary Routing**: Indirect peer bridging (`bridgeIndirectPeer`) tracks rumor intermediaries (`rumorIntermediaries: Map<string, string>`) and enforces an aggressive 2.5-second retry interval (reduced from 15s). During heartbeats, if unverified rumors exist, the node re-announces targeted broker signals (`signalingManager.reannounce(topic, rumorId)`) and relays `mesh_hello` through the intermediary peer every 2.5s (reduced from 20s) until direct WebRTC is established, completely eliminating 3+ participant split-brain mesh partitions.
- **High-Availability MQTT Pool & Broker Immunity**: `DEFAULT_MQTT_RELAY_URLS` establishes 4 verified public brokers (`public.cloud.shiftr.io`, `broker.emqx.io:8084`, `broker-cn.emqx.io:8084`, `test.mosquitto.org:8081`), completely removing unresponsive brokers (e.g. `broker.hivemq.com:8884` which caused connection stalls and false watchdog failover). Combined with an expanded STUN server pool (Cloudflare, Mozilla, and Google STUN 1-4), room join and peer discovery are instantaneous and deterministic.
  - **WASAPI Audio Loopback Inactive Guard**: `useAudioFilter.applyFilters` must never invoke `start_audio_capture` if `stateStore.isSharingScreen` is false, preventing idle COM process scanning and 100Hz IPC emissions when not broadcasting.
  - **Tokio Runtime Sizing**: Local single-client WebSocket servers in Rust must use `tokio::runtime::Builder::new_current_thread()` instead of `new_multi_thread()` to avoid spawning 32 OS worker threads on high-core CPUs (e.g. Ryzen 9 7950X).
  - **Layout Thrashing Prevention**: `RoomVideoContainer` must diff peer IDs and layout mode before running FLIP animation measurements (`getBoundingClientRect()`) to prevent synchronous WebView2 reflows on non-layout state ticks.
- `[Desktop]` **Windows PE Executable & NSIS Installer Icon Embedding**: In Tauri v2 on Windows, the application icon (`icons/icon.ico`) is embedded into the Windows PE binary resources (`32512 ICON ...`) during `tauri-build`. Because Cargo tracks changes only in `build.rs` or declared paths, changes to `icons/` or `tauri.conf.json` do not trigger resource recompilation unless `cargo:rerun-if-changed=icons/icon.ico` and `cargo:rerun-if-changed=tauri.conf.json` are explicitly printed in `src-tauri/build.rs`, and `tauri_build::WindowsAttributes::new().window_icon_path("icons/icon.ico")` is provided. Additionally, the NSIS installer icon is not automatically inferred from `bundle.icon` and must be explicitly configured in `tauri.conf.json` under `bundle.windows.nsis.installerIcon: "icons/icon.ico"`. Stale resource objects should be invalidated with `cargo clean -p p2sharer --release` when changing icons.
- `[UI]` **Chat System Notices and Verified Names**: `GroupRoomManager` records a direct WebRTC arrival but calls `onPeerJoined` only after that peer's direct presence action supplies a nonempty username. `announcedPeerNames` prevents duplicate notices and supplies the last resolved name for leave; a peer that disconnects before sending a name produces no synthetic ID notice. `RoomService` uses short entry, exit, room, and password text. `ChatPane` renders system notices as plain, muted single-line text with a timestamp, ellipsis, and a full-text title; no border, colored background, or welcome copy. Notices are local and do not consume WebRTC chat bandwidth.
- `[Desktop & UI]` **Frameless Multi-Window Picture-in-Picture (PiP) Architecture**: P2Sharer provides native, multi-window Picture-in-Picture independent of browser-native PiP APIs. Popout windows are created via Tauri v2 (`pip_manager.rs`) with frameless configuration (`decorations: false`, `resizable: true`, `always_on_top: true`, `inner_size: 800x480`, `min_inner_size: 320x180`, `shadow: true`). The window features a full-bleed, edge-to-edge video layout with a floating hover overlay (`.pip-overlay`) containing a custom draggable top bar (`.pip-top-bar`, `data-tauri-drag-region`), title, always-on-top toggle (`set_pip_always_on_top`), internal close button ("X"), stats HUD, and standardized controls pill. Signaling between the main window and secondary PiP windows uses dual Tauri IPC events (`pip-signal-${peerId}`) and `BroadcastChannel`, while media is streamed via WebRTC loopback configured with `buildIceServers()` STUN pool to eliminate Chromium mDNS candidate resolution failures between distinct WebView2 processes. When a stream is popped out, the main app's video card transforms into a dedicated placeholder (`.pip-broadcaster-placeholder`) matching the broadcaster radar design with a "Restaurar para o App" action button, while local audio playback is muted in the main app to prevent audio echo. In `src-tauri/src/lib.rs`, `WindowEvent::CloseRequested` must strictly verify `if window.label() == "main"` before calling `std::process::exit(0)`; closing secondary PiP windows emits a `pip-window-closed` event and restores the stream to the main app without terminating the application.
