# Room Apps

Desktop playlist imports first use the fixed-endpoint `load_youtube_playlist` Tauri command. It retrieves the public YouTube page without account cookies, parses literal or hex-escaped initial JSON without executing scripts, and follows browse continuation tokens until completion or the existing 200-video cap. Requests have time/size bounds; IDs and response entries are validated, unavailable videos are skipped, and duplicate entries retain their order. Invidious remains a fallback, but metadata-only HTTP successes and malformed/empty pages are rejected so another provider can be attempted. Pagination uses raw page size rather than the number of validated videos. Imports that would overflow the current queue show a localized error instead of silently truncating or doing nothing.

The native reader searches all `ytcfg.set` data objects for browse context and finds continuation commands inside command-executor wrappers. Offline fixtures exercise provider failover, metadata-only response rejection, and pagination with unavailable entries.

YouTube discovery excludes generated radio/Mix queue IDs with the `RD` prefix from importable playlists. `parseYouTubeInput` retains the selected `v`/short-link video ID but omits the Mix `list` ID, bypassing Invidious playlist retries and the invalid playlist preview. The same predicate filters discovery results and guards playlist preview/import APIs before any network request. Ordinary playlist links retain both video and playlist previews; `start_radio` alone does not suppress a normal playlist.

Live timeline sampling is centralized in `sampleYouTubeTimeline` for the main and PiP players. A current position beyond a cached duration also identifies a broadcast. Once identified, its displayed edge advances with elapsed wall time even while paused or watching past DVR footage, and remains at least the current position. A video change resets the edge estimate. Explicit seeks are consumed before invoking the iframe (including zero-second seeks and polling recovery after buffering), even before live detection, so reentrant player events and unavailable DVR keyframes cannot repeatedly apply the same command. The controls use the same bounded duration for their seek bar and time readout. These estimates do not expose the iframe's unavailable DVR start boundary.

Live YouTube broadcasts use the same main/PiP reconciler but do not seek on heartbeat drift, playback toggles, or buffering recovery. The reconciler detects the documented growth of `getDuration()` over time, shares an optional `isLive` queue flag, and loads a fresh broadcast without a forced zero-second start. Initial resume events leave the default position untouched while the first duration samples arrive. Explicit room seek commands remain supported and are consumed once, including deferred commands after buffering, so DVR clamping cannot create a seek loop. Main and PiP sample actual position and growing duration every second; shared controls show `AO VIVO`. YouTube position validation and projection permit broadcasts longer than 24 hours while other media keep their existing bounds. `youtube_live.test.ts` covers default-edge loading, repeated buffering recovery, one-time manual seek, play/pause continuity, fixed-duration detection, and multi-day timeline validation. Real live iframe playback and two-instance live seeking still require interactive desktop validation.

Queue metadata publications must carry the elapsed playback time forward before resetting the model's receipt clock. `preserveYouTubeTimeline` rebases unchanged position/playing state for queue edits, reorder, saved queue append, and mode switches; seek, playback, heartbeat, replacement, and automatic advance keep their explicit positions. Matching players do not seek during a metadata-only update; periodic synchronization still checks genuine drift. `ended` distinguishes an exhausted queue from an intentional pause and keeps the terminal video's endpoint instead of seeking to zero. `appendYouTubeQueue` starts the first newly appended entry only for an empty queue or ended playback, including saved queue append. Main and PiP ended events publish `auto-advance`; the canonical ActivityToast displays an automatic icon without a participant avatar/name for advance, repeat, and completion. Manual playback continues to use actor toasts. Regression tests exercise changes between heartbeat samples, subsequent periodic reconciliation, mirrored model state, automatic notices, and post-completion additions; live iframe/two-instance runtime playback remains a separate validation step.

YouTube's queue header opens `YouTubeSavedQueuesDialog`, a device-local named queue library stored under `p2sharer_youtube_saved_queues_v1` in WebView local storage. `youtube_saved_queues.ts` validates records, retains order and duplicates, strips historical room attribution, detects name collisions, and persists before notifying subscribers. Save by an existing name or the row's Save action requests overwrite confirmation; rename and deletion update only the library, with deletion confirmed in a separate popup. Import offers replace, append, and cancel. `importYouTubeQueue` rejects overflow above 200 videos rather than truncating, assigns the importing participant as author, preserves playback when appending to a populated queue, and resets to the first video when replacing or appending to an empty queue. One existing model update synchronizes the imported queue to peers; `queue-replace` produces a dedicated activity toast and urgent player/PiP reconciliation. Saving and editing the library do not publish room actions. `ModalDialog` reuses the app's modal styles and entrance/exit animations, portals outside app-card clipping, and contains keyboard focus in the topmost dialog.

YouTube activities can open the existing frameless Windows PiP window through `open_pip_window` with a unique `youtube-<instance-id>` key. The main activity remains the sole P2P state owner and forwards validated room state to `YouTubePipView` over a local Tauri event channel. PiP sends playback commands, progress samples, and ended events back to the main window; only the elected room participant advances the shared queue. The main iframe pauses locally while PiP owns playback and resumes from projected shared time when the native window closes. The PiP close button invokes the existing native `close_pip_window` command, which emits `pip-window-closed` to restore the main player without requiring the WebView window-close ACL permission. Closing or leaving the activity also closes its PiP window. The PiP view reuses `YouTubeControls` and existing window chrome styles; its controls appear on hover.

`src/apps/registry.ts` registers app definitions with a model factory and a lazy view loader. New bundled apps can register their own models and views without changing the transport or room service. Each launch creates a UUID instance; several instances of either kind may coexist. `RoomVideoContainer` renders each instance in the same grid or spotlight stage as peer cards. The app UI is rendered locally for every participant and exchanged as state over the room's `room_apps` Trystero action. No screen video is sent for app cards.

App icons are rendered through `RoomAppIcon`; definitions with `iconStyle: 'filled'` receive no outline stroke prop. This is necessary for the `react-icons` YouTube brand glyph, whose default stroke width is zero. Supplying Lucide stroke widths to that filled SVG distorted it outside the spotlight tray.

The header Apps button opens `AppsModal`, whose icon, description, and banner come from the registry metadata. App cards are clipped to the same grid or spotlight bounds as transmissions. `src/apps/apps.css` owns their responsive layout and containment. YouTube places the player and queue on the left and search on the right when the card is wide; a narrow card offers a local pane switch. Theatre mode is local UI state and expands the player only within its card. The activity header keeps its normal height above the video, while playback controls appear on video hover or keyboard focus. It does not send layout changes to peers. The app card header has a direct Back to grid action. Its three-dot menu contains Leave activity, which unmounts the local app and removes local presence without ending the shared instance, and End for everyone. Grid rows remain vertically centered when app slots are present and fit the viewport; safe alignment keeps overflowing rows scrollable from the top. Local lifecycle callbacks publish one signed chat notice per app start or stop, including the actor and app kind. Remote lifecycle events never republish those notices.

Custom app library banners use the optional `bannerImage` in `RoomAppDefinition` and bundled assets registered in `registry.ts`. Responsive cover cropping can trim the edges; keep essential artwork near the center.

`PersistentRoomApps` mounts each joined app view once in a stable layer within `RoomVideoContainer`. Grid, spotlight, and tray render measured slots; the app card changes position and compact styling without moving or remounting its iframe. Participation is opt-in per instance. Outside participants see a join panel and do not mount the app view or YouTube iframe; joined participants see a compact video preview in unfocused cards. `RoomAppsService` exchanges actor-bound presence events, answers late-peer sync with local presence, and clears disconnected actors. Header avatar initials follow the existing room slot colors and show names through the common tooltip. The YouTube IFrame API's native play and pause events are published to the shared model when they differ from room state. Volume is local per device. YouTube's embed may still display its own metadata and related-video controls; its API does not provide a supported way to remove them.

The Watching filter includes locally joined app instances alongside subscribed streams. Joining or leaving updates both the visible grid or spotlight slots and the filter count immediately. `PersistentRoomApps` still receives every app instance so a joined player stays mounted when a filter hides its slot.

`GroupRoomManager` subjects the action to its existing direct peer verification and admission wrapper. The action carries start, stop, generic app data, and targeted sync messages. `RoomAppsService` owns instance lifecycle and routes data to the registered model. Peers exchange snapshots when a participant arrives; notes use Yjs CRDT updates so simultaneous edits converge. YouTube state uses a Lamport clock and actor tie break; the smallest joined actor publishes playback position every ten seconds. Each joined player independently checks drift on the same interval, projecting the shared position from local receipt time. Routine drift up to four seconds is tolerated, with an eight-second seek cooldown. Play/pause and manual seek events request tighter immediate correction around 0.75 seconds. Resuming after buffering checks drift before the leader can publish another position. Playback speed is not modified. Browser autoplay rules and network delay prevent frame accurate synchronization.

The notepad uses Tiptap with Yjs XML fragment updates for shared rich content and Yjs awareness for remote caret labels and selections. It opens local `.html`, `.md`, and `.txt` files through native Tauri commands in `src-tauri/src/note_files.rs`; saving uses HTML to preserve rich formatting. Opening a file replaces the shared document. The file itself is not transmitted, only the edited document state. The legacy Yjs plain-text field remains in the model for compatibility with existing tests and older snapshots. The YouTube app accepts video and playlist links without an API key and shows preview results before any queue mutation. Video titles use YouTube's oEmbed endpoint; playlist titles, counts, and thumbnail IDs come from public Invidious instances when available. Keyless text search and playlist import use the public Invidious API through a fixed list of instances from its official catalog, validating IDs and titles before they enter shared state. These public services may become unavailable; the UI offers external YouTube search as a fallback. Search terms are sent to the selected Invidious instance, while the shared room message carries only selected video IDs and titles. The player loads Google's IFrame API only after the local actor joins a YouTube activity. CSP allows the required YouTube frame, oEmbed requests, Invidious API requests, and thumbnails. A transparent local hit area handles click-to-toggle and prevents pointer hover from reaching the YouTube iframe, avoiding its hover UI over the app controls. The custom playback deck has a local draft seek state so the visual thumb and time tooltip follow dragging immediately; a completed seek is then sent to the room. Queue moves preserve the currently selected entry and playback position. Repeat-all, repeat-one, shuffle, and remove-played modes are synchronized in the YouTube model. The smallest joined actor advances at video end and publishes playback time, allowing controller handoff after a participant leaves. The embed requests captions off with `cc_load_policy: 0`; the local caption toggle also attempts to load/unload the YouTube captions module when present. That module control is not documented as a supported caption toggle and may stop working if YouTube changes it. Google's IFrame API no longer supports querying or setting playback quality, so the app cannot present a functional quality selector.

Room app state currently exists only in the memories of connected admitted peers. If every peer leaves, app instances and notes disappear unless a participant saved a note locally. This follows the room's P2P only state policy.


The featured app header offers an ExternalLink action that detaches the entire joined app into the existing native window host using a separate `app-<instance-id>` key. `useAppWindow` keeps the main window as the room transport/model owner; `RoomAppWindow` mounts one mirrored view and sends local model updates back over targeted Tauri events. Initial snapshots and participant membership bootstrap the mirror, and ongoing snapshots preserve YouTube receipt time so handoff does not reset projected playback. Main-window app views unmount while detached, leaving a restore placeholder in their persistent card. Leaving, stopping, room teardown, or closing the native window restores or disposes the mirror. Detaching YouTube closes its player-only PiP first; external app teardown also closes any player PiP opened inside it. Model regression tests cover bidirectional note updates, room actor identity, participation gates, and YouTube clock continuity. Interactive native-window and live YouTube checks remain separate from packaging/model validation.


Detached app placeholders retain the compact card focus overlay, allowing grid/tray selection without closing their external window. The explicit restore button sits above that overlay with the shared placeholder-action recipe, so restore and spotlight focus remain independent actions.


Personal room apps use optional local-only `RoomAppInstance.personal` metadata. The library selects a kind by card, then launches from a footer with a default-off "Somente para mim" switch. Personal launches join the local actor immediately. `RoomAppsService` excludes these instances from room sends, snapshots, presence, closed-ID history, and lifecycle chat callbacks; incoming room updates and tombstones cannot affect them. Leaving a personal instance disposes it. Detached windows bootstrap through `initializeLocalView` and forward model edits over targeted device-local Tauri events; the main service retains the room-send privacy gate. Unit tests cover notes, awareness, YouTube, late-peer synchronization, mixed shared/personal instances, hostile room packets, detached edits, and teardown.
