# Consent-Based Chat File Transfer

## Offer and identity

`GroupRoomManager.offerFile` publishes a signed chat message containing only the display name, byte size, SHA-256 digest, and image flag. `PeerAuthenticator.signedChatData` binds those fields to the room, message author, and revision. The native `chat_files.rs` module retains the selected path behind a random local source ID and remembers the path under the room and message IDs in the user's local app data. The path is never included in chat or history.

## Request and transfer

Chat files have no product size cap. File sizes and offsets must be nonnegative exact JavaScript integers (up to `Number.MAX_SAFE_INTEGER`), matched by the native IPC boundary. Native sources, SHA-256 hashing and downloads stream bounded blocks to keep memory independent of total file size. In-memory image previews retain their separate 16 MiB limit; clipboard snapshots and file selection counts also keep their own bounds.

`useChatFileInput` routes the attachment picker, Tauri WebView drag-drop events, and Ctrl+V through the existing `ChatFileOfferDialog`, queueing multiple files for individual confirmation. Native drag coordinates are converted from physical pixels before checking the visible chat rectangle. `arboard` reads native clipboard file lists and static images. GIF paste prefers original DOM file bytes, a GIF image source in copied HTML, or a registered Windows GIF clipboard format before falling back to a PNG bitmap snapshot. HTTP GIF sources have time and byte bounds and are validated by signature and dimensions; encoded GIF bytes remain unchanged. Snapshots live under local app data so future consent requests do not depend on the current clipboard. Native image copying retains GIF bytes alongside the static bitmap format. Cancelling an unoffered snapshot deletes it; published snapshots remain available like other local sources. Plain text paste keeps the normal editor behavior. Desktop gesture behavior still requires an interactive Windows runtime check.

A recipient chooses the automatic Downloads/P2Sharer Downloads destination or a native Save As dialog before sending a request. The request and every file control packet are signed with the sender's room identity and targeted to one verified, admitted direct WebRTC peer whose pinned public key matches the offer's author key. This key binding also works when a returning author has a new transport peer ID. The author sees the original source path and requester name and must accept, unless the offer's local ten-minute auto-accept period remains active. Before acceptance, native code rescans the source and compares its size and SHA-256 with the signed offer. A source restored from an earlier app session follows the same check.

On the WebRTC path, the sender transmits 15 KiB wire blocks from its locally selected source with up to 192 blocks outstanding. The wire uses binary chunks rather than base64 JSON: each chunk has a bounded header with its offset, SHA-256, and author signature. Consent, readiness, cancellation, and acknowledgments remain signed Trystero actions. After consent, both peers open a reliable unordered negotiated WebRTC channel with the same ID; the receiver signs a readiness control packet only after its channel opens, and only then does the sender transmit file blocks. Each signed block fits below 16 KiB including its header, and the sender also checks the negotiated `maxMessageSize`. The recipient verifies the chunk digest and signed identity before queuing out-of-order arrivals by offset, then cumulatively acknowledges contiguous bytes only after writing them. The receiver writes to a temporary file and checks total size and the offer's SHA-256 before renaming it to the chosen destination. Either side can cancel. Incoming requests do not contain paths and cannot invoke native source reads or destination writes directly. A completed download can be revealed in Explorer through its native completion ID while its local file remains present. Live progress samples acknowledged bytes per second and can display decimal MB/s or Mb/s according to a local setting. The transfer menu also displays the selected ICE route and round-trip latency so slow direct routes can be distinguished from TURN relays. Actual throughput still depends on the individual peer connection and available uplink. The app is preproduction, so the current wire protocol has no older-version compatibility branch.

For images up to 16 MiB, the viewer may request an in-memory preview by clicking its placeholder control. This request follows the same sender consent gate. The receiver checks the full SHA-256 before exposing a blob URL to the chat viewer, and revokes that URL when leaving the room. The verified bytes remain in memory so Save and Save As can write them locally without a second peer request; native completion checks the digest again before exposing the saved file.

Own sent images also expose Save and Save As, including clipboard PNG snapshots retained in app data. `GroupRoomManager.getOwnImageSource` checks local signing-key ownership, deletion/revocation, and source size/hash/path, using the shared source restoration helper for historical offers. `RoomService.saveLocalImage` shares the existing native destination, progress, cancellation, completion digest, and Explorer-reveal flow between verified cached bytes and local source chunks. Local source saves do not contact peers and are independent of the 16 MiB preview limit. Model tests cover historical-source restoration, a larger-than-preview image, native destination cancellation, source changes, cancellation during reads, and remote/deleted ownership gates; DOM tests cover both save choices on own images.

## Browser streaming file transfers

In the web runtime, files are handled without cumulative size or batch limits:
- **Streaming send**: Browser-selected files remain disk references as DOM File handles. Initial SHA-256 digests use crypto.subtle.digest for files under 32 MiB and stream 4 MiB slices with an incremental SHA-256 state machine for larger files, yielding periodically to prevent main-thread stutter. Chunk reads use lazy File.slice(), keeping sender memory bounded regardless of total size.
- **Direct disk write (Chromium)**: Where the File System Access API is supported (showSaveFilePicker), the user chooses the destination before transfer begins. Incoming chunks stream directly to disk via FileSystemWritableFileStream while an incremental hasher tracks SHA-256. Upon completion, the stream closes and verifies the digest; upon cancellation, .abort() removes the incomplete file.
- **In-memory fallback**: Environments without File System Access API buffer incoming chunks in memory and trigger a browser download upon digest verification.

## Native direct bulk transport

After source consent and the existing source size/hash check, `chat_file_direct.rs` can offer a one-use TLS/TCP stream bound to the selected local host candidate. `core/chat_file_direct.ts` checks the selected local host route and a remote host or peer-reflexive candidate. The sender binds its selected native address; the signed acceptance includes that numeric endpoint. The recipient checks an exposed remote address when available. Chromium can omit a peer-reflexive remote address: in an explicit LAN room or a global IPv6 route, the recipient can use the signed numeric endpoint and pinned certificate instead. Hostnames, URLs, loopback and unusable address classes are rejected. NAT-mapped and TURN routes retain the WebRTC bulk transport. A directly reachable IPv6 host can also use TLS across networks; this does not bypass a router firewall.

The signed `chat-file-control-v3` acceptance binds the numeric address, ephemeral certificate, port and random capability. The recipient trusts that exact certificate and validates the TLS server name; the capability is sent only inside TLS. Listeners expire after twenty seconds, allow at most eight authentication attempts, and close after one authenticated connection. Native state bounds concurrent tasks, and transfer cancellation, peer removal and room exit abort their tasks. The sender opens only its selected native source ID; the receiver writes only its consent-created download ID with existing contiguous-size bounds. File bytes stay outside WebView IPC. The native receiver coalesces TLS fragments into at most 256 KiB disk writes, flushing earlier for progress on slow links; its timeout applies to individual stalled reads rather than imposing a minimum throughput. TLS protects stream records; completion still requires the signed offer's complete SHA-256 before the final signed acknowledgment. The native stream does not add per-block application signatures.

Connection failure before any destination bytes are written falls back to the signed WebRTC readiness handshake. The sender then suppresses new native offers on that same peer connection for five minutes, avoiding a connection timeout for every file on a blocked route. A failure after partial native writes cancels the transfer rather than appending an incompatible fallback stream. Image previews keep their bounded in-memory WebRTC path. Native transport diagnostics identify TLS/TCP instead of attributing its bytes to the room's UDP channel. The direct optimization does not provide TCP NAT traversal and is not a claim about measured WAN throughput.

## Native I/O and receiver concurrency

`CHAT_FILE_IO_BATCH_BYTES` groups up to sixteen 15 KiB wire blocks into a 240 KiB native read, below the existing Rust command's 256 KiB limit. Signing preparation runs concurrently within this bounded batch; channel sends still respect the acknowledgment window and transport backpressure. The receiver coalesces contiguous verified blocks into bounded native writes and sends cumulative acknowledgments only after writing them. Sparse arrivals must drain without waiting for a full batch, or a partially filled sender window could deadlock.

Network transfers use `core/chat_file_io.ts` to keep native IPC binary: `read_chat_file_bytes` returns an ArrayBuffer and `write_chat_download_bytes` receives a raw body with a bounded local download ID and unsigned byte offset in headers. Native commands retain the same selected-source and consent-created destination maps, chunk limits, contiguous-write checks and completion digest. Downloads keep their file handle open until completion or cancellation; close it before hashing/renaming or removing the temporary file on Windows. The base64 commands remain for the local image-save path and share the same native read/write helpers. IPC batching does not enlarge the signed network messages.

`FileSession.writingUntil` covers only blocks already removed from the pending map for an in-progress write. Reject duplicates below that boundary before and after asynchronous signature verification. The broader `receiving` flag remains set while signing/sending an acknowledgment: using it to reject a block at the newly advanced `session.offset` discards the legitimate next block and can permanently stall a reliable transfer. The acknowledgment-race regression exercises real signed packets with a deliberately pending acknowledgment.

## Availability limits

An offer contains no file bytes and historical offers need the original author online with the original file present. A disconnected peer cannot prove it has seen every later room revocation; this is an existing P2P room authorization limit. A modified local client can always choose to share its own data or decline requests, but cannot impersonate another admitted author's signed offer or pass a changed file through the recipient's SHA-256 check. End-to-end transfer behavior needs a two-instance desktop check; unit tests cover message and control signatures plus native digest and name validation.

## Local WebRTC throughput reproduction

`test/bench/chat_file_webrtc.html` opens two real RTCPeerConnections over local ICE and uses Trystero's installed action-wire implementation for comparison with the current dedicated bulk channel. Its signed path uses the current 15 KiB block size and 192-block window. The full path includes base64 conversion to approximate native IPC, SHA-256 and ECDSA per chunk, acknowledgments, out-of-order buffering, and a final whole-file digest. It does not invoke Tauri commands, write to disk, negotiate a real room, reproduce a remote ICE route, or exercise the production native I/O batching and receiver concurrency guards.

Distinguish SCTP/channel behavior from the selected network route before assigning a throughput bottleneck; loopback benchmarks do not establish WAN performance.

Throughput diagnosis separates native reads, signing/preparation, channel queueing, verification, writes, and acknowledgments. Confirm the actual buffer threshold after channel initialization and immediately before sends; third-party initialization can overwrite an earlier setting. A larger queue alone does not establish faster transfer. The dedicated bulk path separates signed blocks from room control; bounded 15 KiB blocks avoid relying on SCTP message interleaving, and the 192-block window keeps outstanding bytes bounded. Compare against the same remote route before claiming a WAN improvement.
