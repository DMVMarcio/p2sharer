# Consent-Based Chat File Transfer

## Offer and identity

`GroupRoomManager.offerFile` publishes a signed chat message containing only the display name, byte size, SHA-256 digest, and image flag. `PeerAuthenticator.signedChatData` binds those fields to the room, message author, and revision. The native `chat_files.rs` module retains the selected path behind a random local source ID and remembers the path under the room and message IDs in the user's local app data. The path is never included in chat or history.

## Request and transfer

A recipient chooses the automatic Downloads/P2Sharer Downloads destination or a native Save As dialog before sending a request. The request and every file protocol packet are signed with the sender's room identity and targeted to one verified, admitted direct WebRTC peer whose pinned public key matches the offer's author key. This key binding also works when a returning author has a new transport peer ID. The author sees the original source path and requester name and must accept, unless the offer's local ten-minute auto-accept period remains active. Before acceptance, native code rescans the source and compares its size and SHA-256 with the signed offer. A source restored from an earlier app session follows the same check.

The sender reads 15 KiB blocks from its locally selected source with up to 192 blocks outstanding. The wire uses binary chunks rather than base64 JSON: each chunk has a bounded header with its offset, SHA-256, and author signature. Consent, readiness, cancellation, and acknowledgments remain signed Trystero actions. After consent, both peers open a reliable unordered negotiated WebRTC channel with the same ID; the receiver signs a readiness control packet only after its channel opens, and only then does the sender transmit file blocks. Each signed block fits below 16 KiB including its header, and the sender also checks the negotiated `maxMessageSize`. The recipient verifies the chunk digest and signed identity before queuing out-of-order arrivals by offset, then acknowledges each block only after writing it. The receiver writes to a temporary file and checks total size and the offer's SHA-256 before renaming it to the chosen destination. Either side can cancel. Incoming requests do not contain paths and cannot invoke native source reads or destination writes directly. A completed download can be revealed in Explorer through its native completion ID while its local file remains present. Live progress samples acknowledged bytes per second and can display decimal MB/s or Mb/s according to a local setting. The transfer menu also displays the selected ICE route and round-trip latency so slow direct routes can be distinguished from TURN relays. Actual throughput still depends on the individual peer connection and available uplink. The app is preproduction, so the current wire protocol has no older-version compatibility branch.

For images up to 16 MiB, the viewer may request an in-memory preview by clicking its placeholder control. This request follows the same sender consent gate. The receiver checks the full SHA-256 before exposing a blob URL to the chat viewer, and revokes that URL when leaving the room. The verified bytes remain in memory so Save and Save As can write them locally without a second peer request; native completion checks the digest again before exposing the saved file.

## Limits

An offer contains no file bytes and historical offers need the original author online with the original file present. A disconnected peer cannot prove it has seen every later room revocation; this is an existing P2P room authorization limit. A modified local client can always choose to share its own data or decline requests, but cannot impersonate another admitted author's signed offer or pass a changed file through the recipient's SHA-256 check. End-to-end transfer behavior needs a two-instance desktop check; unit tests cover message and control signatures plus native digest and name validation.

## Local WebRTC throughput reproduction

`test/bench/chat_file_webrtc.html` opens two real RTCPeerConnections over local ICE and uses Trystero's installed action-wire implementation for comparison with the current dedicated bulk channel. Its signed path uses the current 15 KiB block size and 192-block window. The full path includes base64 conversion to approximate native IPC, SHA-256 and ECDSA per chunk, acknowledgments, out-of-order buffering, and a final whole-file digest. It does not invoke Tauri commands, write to disk, negotiate a real room, or reproduce a remote ICE route.

On 2026-09-29, the Windows integrated browser moved 55 MiB over direct loopback in 7.16 seconds (8.06 MB/s) with the raw 64 KiB buffer, 6.28 seconds (9.18 MB/s) with the 4 MiB buffer, and 8.43 seconds (6.84 MB/s) with the signed path. The selected candidate pair was direct with about 1 ms RTT. Sender preparation took 2.54 seconds cumulatively and recipient verification 0.095 seconds; this does not support signature verification as the explanation for remote rates of 0.25 MB/s and 2.00 MB/s. The user observed one remote transfer at roughly 0.2 MB/s on a selected direct route with 40 ms RTT, so neither relay use nor round-trip time alone explains that case. The app now accumulates native read, sender preparation, data-channel send, recipient verification, recipient write, and acknowledgment times during real transfers. A two-instance native check and these per-stage measurements on the slow peer remain necessary to identify the peer-specific bottleneck.

On the direct 44 ms peer, a 55 MiB transfer reached about 5.3 MiB in 21.9 seconds: sender read took 0.1 seconds, preparation 0.0 seconds, and data-channel send 21.9 seconds; receiver verification and acknowledgment were negligible and disk write took 0.5 seconds. This isolates the delay to Trystero/WebRTC flow control or the remote network path, not file signatures. Trystero 0.25.3 sets a 65,535-byte low-water mark and pauses its 16 KiB action frames when the channel buffer exceeds it. `FileOptimizedPeerConnection` raises that mark to 1 MiB for the room's Trystero data channel after Trystero initializes it. The larger window aims to keep a direct WAN path busy, but its remote throughput impact must be measured with the same peers; it also allows more queued chat/control traffic behind file data.

The user repeated the transfer with the 1 MiB setting and observed the same approximately 0.24-0.26 MB/s rates and stage times; write time varied to 0.9 seconds. The increased queue alone is not the limiting factor. The transfer menu now samples the selected ICE candidate protocol/types, local data-channel buffer and threshold, and candidate-pair bytes per second every five seconds. It shows the whole peer connection's rate, which may include screen/audio traffic, and cannot directly report data-channel packet loss. If the queue stays full while connection bytes match file throughput, investigate actual uplink, VPN, TCP ICE, or path loss. If the queue stays empty while channel send time grows, investigate application/Trystero scheduling. Check both users' upload speed in Mb/s rather than inferring it from advertised download plans.

Sender bandwidth and local preparation were independently checked during diagnosis. Distinguish SCTP/channel behavior from the selected network route before assigning a throughput bottleneck; loopback benchmarks do not establish WAN performance.

The next diagnostic screenshots showed a direct 22 ms UDP/srflx-to-srflx route with file throughput of 1.2-1.3 MB/s and whole-connection WebRTC throughput of 1.5-1.6 MB/s. Crucially, the sender's data-channel threshold was still 64 KiB, so the earlier claimed 1 MiB change had not actually reached this channel. The inbound `datachannel` listener may run before Trystero's own handler resets the threshold; applying it in a microtask was insufficient. `ensureFileDataChannelWindow` now sets and checks the 1 MiB threshold immediately before each chunk send, and the channel-open handler also applies it. The next remote test should first confirm the displayed threshold, then compare throughput. A threshold improvement remains a hypothesis until measured on the same route.

The subsequent direct 46 ms UDP/srflx-to-srflx test showed the intended 1 MiB shared channel threshold and a full 1 MiB sender queue, but only 0.28 MB/s of WebRTC throughput and 0.27 MB/s of file throughput; the receiver saw about 0.26 MB/s. This rules out Trystero's 64 KiB threshold as the main cause for that peer. `FileBulkChannelManager` now carries 48 KiB signed blocks over a separate reliable unordered negotiated channel on the same RTCPeerConnection, while control traffic stays on Trystero. A signed receiver readiness packet prevents sending before both ends create the negotiated channel. The change removes Trystero's 16 KiB framing and shared-channel head-of-line pressure, but still uses the same underlying SCTP/ICE path; remote throughput must be measured again before claiming a speed improvement.

The updated benchmark ran inside Codex's internal browser over a real local WebRTC connection with 16 MiB. The signed Trystero path reached 7.51 MB/s, the same path with its 1 MiB threshold reached 7.67 MB/s, and the signed dedicated bulk path reached 7.71 MB/s; all matched the final SHA-256. The local difference is small and does not establish remote improvement. The result was captured through `test/bench/result_receiver.mjs` listening only on localhost; no external browser window was controlled. The desktop build remains the product validation gate.

Repeating the same real local WebRTC benchmark with 55 MiB gave 7.43 MB/s for the signed Trystero path with the 1 MiB threshold and 9.28 MB/s for the signed dedicated bulk path, about 25% higher on this loopback run; both matched the final digest. The benchmark did not use Tauri IPC, disk I/O, or the user's remote network route, so it does not predict the remote rate. The 16 MiB and 55 MiB results differ enough that the remote pair must be tested before drawing a WAN conclusion.

The first remote test of the dedicated channel still peaked at only 0.35 MB/s. At roughly 46 ms RTT on a direct UDP/srflx-to-srflx pair, the sender reported 0.23 MB/s file progress, 0.29 MB/s WebRTC throughput, a 1.1 MiB channel queue, 0.4 seconds reading, 0.1 seconds preparing, and 30.8 seconds waiting on the channel. The receiver reported 0.28 MB/s file progress and 0.23 MB/s WebRTC throughput, with 0.1 seconds verifying, 0.9 seconds writing, and negligible ACK time. The dedicated channel removes Trystero framing as the likely bottleneck for this peer. RFC 8831 recommends keeping data-channel messages at or below 16 KiB without guaranteed SCTP message interleaving. The file block is now 15 KiB plus a bounded signed header, with 192 blocks in flight to retain approximately the same byte window. This tests the fragmentation hypothesis; its remote throughput effect is unverified.
